# Luna

SaaS для управления обувным производственным цехом: сотрудники и сдельная зарплата,
заказы, склад, продажи, касса, себестоимость и аналитика. Рабочие отчитываются
о выработке через Telegram-бота, владелец управляет всем из мобильного приложения.

**Стек:** Flutter (Android-first) · NestJS (Node.js 20, TypeScript) · PostgreSQL 16 · Redis · REST.

## Запуск приложения

```bash
cd app
flutter pub get
dart run build_runner build --delete-conflicting-outputs
flutter run
```

Адрес API определяется платформой: с Android-эмулятора это `10.0.2.2`
(его шлюз к машине разработчика), в остальных случаях `localhost`.
Для физического устройства адрес передаётся явно:

```bash
flutter run --dart-define=API_BASE_URL=http://192.168.1.5:3000/api/v1
```

Проверки: `flutter analyze` и `flutter test`.

## Запуск

```bash
cd backend
cp .env.example .env          # укажите DATABASE_URL и JWT_SECRET
npm install

docker compose up -d          # postgres + redis

npx prisma migrate dev        # создаст таблицы

# CHECK-констрейнты, partial-индексы и триггер сверки склада —
# отдельной миграцией, т.к. Prisma их не генерирует
npx prisma migrate dev --create-only -n constraints
cat prisma/sql/002_constraints.sql >> prisma/migrations/*_constraints/migration.sql
npx prisma migrate dev

npm run seed                  # демо-данные
npm run start:dev             # http://localhost:3000/api/v1
```

**Демо-вход после seed:** `+998901234567` / `luna12345`

### Проверочные сценарии

Помимо модульных тестов (`npm test`) есть сценарии в `test/`: они запускаются
вручную на живой БД и печатают результат построчно. Проверяют то, что не
поймать без настоящей базы — транзакции, констрейнты, согласованность склада
и кассы. Каждому нужен применённый seed.

Изоляция арендаторов — самый критичный механизм системы: данные одного цеха
не должны быть видны другому.

```bash
npm run test:tenant
```

Полный сценарий Telegram-бота без обращения к серверам Telegram: привязка
по коду, отчёт о выработке, идемпотентность ретраев, сводки, отмена.

```bash
npm run test:telegram
```

Полный путь зарплаты: выработка → начисление → аванс → закрытие периода.
Проверяет идемпотентность пересчёта, захват выработки при закрытии
(защита от двойной оплаты) и то, что ведомость сходится с кассой.
Заводит собственные данные и убирает их за собой.

```bash
npm run test:payroll
```

Касса и расходы. Главный инвариант — баланс кассы равен сумме её движений;
разойтись они могут только там, где кто-то тронул `balance` мимо общего
механизма, и поймать это можно лишь на настоящей базе.

```bash
npm run test:cash
```

Идемпотентность денежных операций. Поднимает настоящее приложение на своём
порту и опрашивает по HTTP — включая два одновременных нажатия «Сохранить»:
защита живёт в интерцепторе, и модульным тестом её не подтвердить.

```bash
npm run test:idempotency
```

Заказы и продажи. Продажа одновременно двигает склад, кассу и фиксирует
себестоимость; выдача заказа делает то же, не списав товар дважды. Ошибка
в любой из этих связок обнаружилась бы только при инвентаризации.

```bash
npm run test:sales
```

Аналитика. Проверяется не «эндпоинт отвечает», а что цифры сходятся с тем,
из чего собраны: прибыль равна выручке минус себестоимость, расходы и выплаты,
зарплата входит по выплатам, сторнированная продажа выпадает отовсюду.

```bash
npm run test:analytics
```

Отчёты и уведомления. Проверяет то, что не поймать без настоящей базы:
файл собирается по данным своей компании (фоновая генерация легко теряет
tenant-контекст), суммы в XLSX записаны числами, шрифт PDF покрывает и
кириллицу, и латиницу с цифрами, а сторож уведомлений не заваливает ленту
повторами.

```bash
npm run test:reports
```

Уборка счётчиков лимита и просроченных диалогов — проверка, что хранилища
в памяти не растут бесконечно. БД не требуется.

```bash
npm run test:cleanup
```

### Telegram-бот

Для работы бота задайте в `.env`:

```
TELEGRAM_BOT_TOKEN=<токен от @BotFather>
TELEGRAM_BOT_USERNAME=<имя бота без @>
TELEGRAM_WEBHOOK_SECRET=<openssl rand -hex 16>
TELEGRAM_WEBHOOK_URL=<https-адрес сервера>   # пусто в dev → режим polling
```

Привязка рабочего: в приложении открыть сотрудника → «Подключить Telegram» →
показать QR или продиктовать код → рабочий отправляет боту `/start <код>`.

## Принятые решения по MVP

- **Без размерной сетки** — модель обуви = товар. Схема готова к расширению
  через `product_variants` аддитивной миграцией.
- **Автоподтверждение выработки включено** по умолчанию (`companies.work_log_auto_approve`).
  Отчёт из Telegram сразу идёт в зарплату; при желании владелец включает
  обязательное подтверждение в настройках.
- **Основной язык — узбекский**, русский запасной. Язык ответа выбирается
  заголовком `Accept-Language: uz|ru`; тексты — в `src/common/i18n/messages.ts`.

## Что уже проверено на живой БД

- миграция схемы применяется с нуля, все 30 таблиц создаются;
- `002_constraints.sql` накатывается без ошибок;
- **триггер сверки склада** ловит попытку изменить остаток мимо журнала движений;
- `CHECK`-констрейнты не дают уйти в отрицательный остаток и записать выработку,
  где `amount ≠ quantity × rate`;
- регистрация, вход, `/auth/me`, ротация refresh-токена;
- повторное использование отозванного refresh-токена отзывает всю семью токенов;
- нормализация телефона: `901234567` → `+998901234567`;
- **изоляция компаний**: чужие записи не читаются и не изменяются даже при
  точном совпадении ID, `create` без `companyId` берёт его из контекста;
- справочники: операции, товары с флагом низкого остатка, сотрудники, статистика
  выработки по дням и моделям;
- **резолв расценки** от частного к общему: базовая 12 000 сум за операцию,
  16 000 сум для конкретной модели — выбирается более специфичная;
- склад: приход, инвентаризация (сервер сам считает дельту от фактического
  остатка), отказ при нехватке товара с указанием доступного количества;
- **роли**: ADMIN создаёт товары, но получает 403 на удаление; OWNER архивирует,
  и товар исчезает из списков;
- локализация: одна и та же ошибка приходит на узбекском либо на русском
  в зависимости от `Accept-Language`;
- **Telegram-бот целиком**: незнакомый отправитель не получает никаких данных,
  привязка по одноразовому коду, повторное использование кода отклоняется,
  мастер отчёта с пропуском шага операции, быстрый ввод «Sport-12 30»,
  сводки `/today` и `/month`, отмена записи в течение 30 минут;
- **идемпотентность вебхука**: повтор того же `update_id` не создаёт дубль записи;
- подтверждение выработки: пачкой, поштучно, отклонение с причиной; повторное
  подтверждение уже обработанной записи отклоняется;
- защита вебхука: неверный секрет в пути или отсутствие заголовка → 403;
- удаление подтверждённой выработки запрещено — это основание для начисления.
